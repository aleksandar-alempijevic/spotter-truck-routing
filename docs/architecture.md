# Architecture

## What exists now

Two programs that talk over HTTP, in one repository.

```
browser  ──►  Vite dev server (:5173)  ──/api──►  Django on uvicorn (:8000)
 React app     serves the app, proxies /api        Django Ninja endpoints
```

**Backend (`backend/`).** Django 6 with Django Ninja, served by uvicorn over ASGI so views can be `async`. Entry points: `config/asgi.py` (the application object uvicorn serves), `config/urls.py` (mounts the API at `/api/`), `api/api.py` (endpoints). Endpoints: `GET /api/health`, returning `{"status": "ok"}`, `POST /api/routes`, `POST /api/weather` and `GET /api/address-search` (below). Settings live in `config/base.py` and read environment variables; they refuse to start without a secret key unless debug is on. `config/settings.py` loads `.env` and then `base.py`; `config/settings_test.py` skips `.env` and uses dummy keys, so tests never touch real credentials or live APIs. There is no database; the settings declare none.

**Risk and ranking rules (`backend/risk_rules/`).** Plain Python with no Django or HTTP imports: the per-checkpoint risk level (`levels.py`), the route summary (`summary.py`) and the route ranking (`ranking.py`). The weather use case (`api/weather_report.py`) is the only caller, and the only place a `WeatherReading` is built. The API layer imports it and it never imports the API layer, and a test checks that its source imports only the standard library. The rules are explained in [logic.md](logic.md).

**Routes, checkpoints and weather.** The code is split into layers; imports run one way.

```
api ──► providers ──► weather ──► routing (geo only)
 │                       ▲
 ├───────────────────────┘
 └──► risk_rules          (weather, routing and risk_rules import none of each other)
```

- `routing/` is pure computation on a provider-neutral `Route` (geometry, length, travel time, time knots): checkpoints with ETAs, the overlap measure, via-city candidates from a hand-kept list, line reduction for the map, and route order and ids. Standard library only, checked by a test.
- `weather/` is pure computation on provider-neutral types, with the standard library and `routing`'s distances only, checked by a test: the hourly `ForecastSeries` and `conditions_at` (sampling at an instant, below), the 0.1° forecast lattice, the bounded `ForecastCache`, and the corridor grid with `plan_locations`.
- `providers/` is the only package that imports `httpx`, knows a provider's URL and field names, or touches a key. `outbound.py` holds the shared policy: one HTTP client per planning request (opened inside the request's coroutine and closed on every exit, including the cancellation Django's ASGI handler applies on a client disconnect), a cap of 4 calls in flight (the one concurrency cap), one retry on a timeout, transport error or 5xx (never on a 4xx; a call made with `retry=False`, as address search is, is made once), and provider-neutral errors with no URL, key or upstream body in them. Each error class carries its code and its HTTP status, and the API's error handler and declared error responses are read from the classes. The `httpx` and `httpcore` loggers are held at WARNING by the `LOGGING` setting in `config/base.py`, because httpx logs every request URL, key included, at INFO. Besides GET, `post_form` sends a form-encoded body under the same policy (the weather request does not fit in a URL), and a 429's error carries the provider's `Retry-After` as the number `retry_after_s`, never in its message (a 401 or 403 carries none). `tomtom.py` is the TomTom truck-mode adapter, where kilograms exist, `geoapify.py` is the Geoapify autocomplete adapter, and `openmeteo.py` is the Open-Meteo adapter: it needs no key, applies the 7:1 snow ratio, checks the unit strings and the hourly stamps (the first and last are parsed, the rest checked by shape), parses off the event loop, and keeps a null as absent. Geoapify and Open-Meteo each define `ATTRIBUTION_TEXT` and `ATTRIBUTION_URL`; the package exports Geoapify's, and the weather use case reads Open-Meteo's through the module.
- `api/` holds the endpoints (`api.py`), the wire schemas (`schemas.py`) the weather use case (`weather_report.py`, below) and the planner (`planner.py`), which only sequences the awaits: it makes the base call, decides whether to fill, makes the via calls, applies the overlap verdicts and builds the checkpoints. A test feeds the checkpoints into `risk_rules.summarize_route`, so the two packages' contract is checked without either importing the other.

**`POST /api/routes`** takes origin and destination coordinates, a departure instant, the load in pounds and the checkpoint spacing ([assumptions.md](assumptions.md) lists the limits). It asks TomTom for the fastest route and two alternatives. When fewer than three come back, it fills the gap through a via-city: up to three cities on each side of the trip, chosen from a hand-kept list of 45 as at least 120 km from every route already in hand, least detour first, the two sides alternating. Every candidate's call starts at once and the outbound cap lets four run at a time; as each answer arrives it is kept only if it overlaps every route kept so far by less than half. Once three routes are kept the calls still running or waiting are cancelled, so a gap that fills early costs few calls (a call waiting for a slot never starts) and a trip with no distinct third route costs at most six via calls plus the base call. The overlap work and the parsing of TomTom's answers run in threads, so a long route's tens of thousands of points do not block the event loop, and each kept route's near-cells are computed once. The response has one to three routes, fastest first, with ids `route-1` to `route-3` numbered from that order, each with its travel time in seconds, its miles, checkpoints (`mile`, `lat`, `lon`, `eta`), its line for the map as `[lon, lat]` pairs, its `source` (`provider` or `via_city`) and its `via` city. A `shortfall` with a reason and a message says why there are fewer than three: `no_distinct_alternative`, or `fill_incomplete` when the search for another route failed or ran out of its time budget. The message names the cities that were tried. A failed fill never fails the request.

- **One distance scale per route.** A route's miles are TomTom's reported length, and polyline distances are scaled to it, so checkpoint positions and ETA knots agree (TomTom's own polyline length differs from it by up to 2.6 km on a long trip). Checkpoints are placed on the full-resolution line before it is reduced.
- **Checkpoint marks** start at mile 0, ascend strictly and end at the route's total miles. A length that is an exact multiple of the spacing does not get its last mark twice.
- **ETAs** are interpolated between TomTom's turn instructions, which carry cumulative distance and time. A route whose instruction times go backwards, or whose last time differs from the travel time, is rejected as a malformed provider response, never interpolated around.
- **Ids come from sorted order** (travel time, then miles), so the same routes get the same ids whatever order TomTom returns them in.
- **What the weather request sends back** is the response without `line`, `source` and `via`: `load_lb`, `checkpoint_interval_miles`, and per route `id`, `travel_time_seconds`, `total_miles` and `checkpoints`. The schema classes `PlanParams` and `RouteCore` are that subset, and they own its input bounds: the load above 0 and at most 80,000 lb, a spacing of 10, 25 or 50, finite in-range coordinates, a timezone-aware `eta`, and at most 600 checkpoints per route. `RoutesIn` extends `PlanParams`, so the routes request and the weather request share one definition of the plan fields. `WeatherIn` extends `PlanParams` and takes `routes: list[RouteCore]` (one to three), so the two are named parts in the OpenAPI schema and the generated types (the routes schemas still flatten them), and the weather response echoes the plan as a nested `plan: PlanParams`. Extra fields in the body are ignored. The corridor is derived from the checkpoint positions, so no route line travels back; three of the longest test routes (about 10,500 miles together) make about 1,050 checkpoints at 10-mile spacing, roughly 100 kB of JSON.
- **Errors** on every endpoint have one body, `{code, message}`, where `code` is one of a closed set (`validation_error`, `not_found`, `method_not_allowed`, `internal_error`, `no_route`, `provider_timeout`, `provider_unavailable`, `provider_limited`, `provider_not_configured`, `provider_malformed_response`, `provider_error`, `outside_service_area`, `too_many_locations`) that a test ties to every error class, so the generated types carry it as a union. The last two are validation failures that need different advice from the sender, so each has a code of its own and still answers 422: checkpoints outside the service box, and a plan needing more forecast locations than the bound. The API's validation handler picks the code from the error's type, set where the error is raised (`SPECIFIC_VALIDATION_CODES` in `api/errors.py`), never from the message text; any other validation failure stays `validation_error`. Every error the API's own routing and endpoints produce has this body, including the ones no endpoint raises: a request body that is not JSON, or over Django's upload limit, is a 422 `validation_error`; a wrong HTTP method is a 405 and an unknown path a 404; and an unexpected exception is a 500 `internal_error` whose detail goes to the log and never to the client. `api/middleware.py` judges the body, not the layer: any error status under `/api/` whose body is not a JSON object with exactly `code` and `message` (Django's 404 page, Ninja's plain-text 405, a `Http404` raised inside an endpoint) is replaced, and a 405 keeps its `Allow` header. Layers above the API can still answer in another shape: Django's host check (a disallowed `Host`) and the hosting gateway are outside this guarantee, so a client treats an error without a parsable `{code, message}` as an unknown failure. Every operation declares the 404, 405, 422 and 500 responses. A new error status enters through `API_ERRORS` (`api/errors.py`) or a provider error class with a code in the closed set, never through `HttpError` or a framework default; the middleware's 500 plus a warning for any other shape is an alarm for a gap, not a mapping to rely on. Statuses: validation 422 (the two coded refusals included), no route between the points 422, timeout 504, upstream failure or malformed response 502, rate limit or missing key 503. Messages carry no URL, key or provider text and name no single provider.
- **Time budget:** each TomTom call may take 50 s, and one planning request has one 120 s deadline covering the base call and the fill. When the budget runs out during the fill, the routes in hand are returned with the `fill_incomplete` shortfall; during the base call it is a 504.

**`POST /api/weather`** takes the routes response's send-back subset (`load_lb`, `checkpoint_interval_miles` and one to three routes) and answers with the forecast, risk levels, summaries, ranking and corridor grid for those routes, in one request.

- **Validation** runs before any outbound call and answers 422 `validation_error`, except that a checkpoint outside the service box answers `outside_service_area`: unique route ids; every checkpoint inside the service box (latitude 15 to 72, longitude -170 to -50: the contiguous US with margin, Alaska, Hawaii, Puerto Rico and the Canadian corridors a US-to-US route can cross); the first mark at 0, marks strictly ascending and not past `total_miles` (exact comparisons, at least as strict as `summarize_route`, which a table test checks); each mark gap at most the interval; and consecutive checkpoints no farther apart in a straight line than their mark gap (plus 5% and a quarter mile) and no farther apart in longitude than that distance can cover at their latitude, `longitude_span_coverable` in `weather/grid.py` owns that last predicate, next to the sweep it protects: it rejects a jump across the antimeridian that is short on the ground but spans the whole map in the planar sweep (the service box already excludes those longitudes, so this is a second line). The last two keep a hand-built body from making the corridor walk a huge area. A test sends real routes responses at all three spacings, a via-city route included, through the validator. A request that needs more than 1,800 forecast locations (three windows of 600, the most that fits the deadline) is also a 422 with the code `too_many_locations`, raised as Ninja's own validation error (typed `too_many_locations`) so it takes the ordinary 422 path. `plan_locations(max_locations=…)` raises when the total (checkpoint cells plus grid-only cells) passes that number, and earlier, as a cheap path, when the checkpoint cells or the corridor's display cells alone do (both are lower bounds on the total). Stopping at the bound limits the cost of an oversized plan; the work before it stops is a sweep of each segment's bounding box, which is small because validation keeps every segment to road length. Corridor cells whose centre would lie past a pole or the antimeridian (judged on the unclamped centre) are left out of the grid, so no request point is off the map; a checkpoint's own cell is not adjusted, because the service box keeps checkpoints far from both.
- **Weather at a checkpoint** is the series of its 0.1° forecast cell (about 7 miles), sampled at the checkpoint's ETA by timestamp: wind is interpolated between the stamps either side, and gust, rain and snow come from the first stamp at or after the ETA, because each describes the hour before its stamp. An ETA up to an hour before the first stamp reads the first stamp; later than the last stamp (96 hours ahead) there is no forecast. A needed value that is absent also means no forecast. Rain is precipitation less the water in the snow (snowfall divided by 7, Open-Meteo's fixed ratio); snow is the snowfall depth; gusts are shown and never classified. `weather` and `risk` are null together, and a null level means the forecast does not reach that time, never Low. The load is applied by `classify_weather`.
- **Per route** a summary (miles at each level, no-forecast miles, average risk) comes from `summarize_route`. The ranking is `rank_routes` mirrored on the wire (`decided_by`, per-route `vs_first` with what each lost to). `rank_routes` takes one to three routes; a one-route plan has one entry, `decided_by` null and no `vs_first`, and is recommended unless it has No Travel miles ([logic.md](logic.md#3-ranking)).
- **The corridor grid** has a risk level, with the load rules applied, for each hour from 0 to 48. Hour 0 is the top of the request's UTC hour (`grid.start`); the departure is a separate field. Cells are 0.5° (`cell_degrees`; about 35 by 27 miles in the US), sent as centres with one shared size, and a cell's index is its id. Hours are sampled by position in the series: a cached series starts at the request's hour, so grid hour h is its entry h (`conditions_by_hour`; a series that starts at another hour is shifted by the difference). A cell is in the corridor when its centre is within 25 miles of the segments joining a route's consecutive checkpoints. Levels are indexes into `level_codes`, so the browser recolours a cell from the array with no further request. A display cell that holds a checkpoint's forecast cell reads that forecast, so only cells with no checkpoint add a location. The worst measured case, three cross-country routes at 25-mile spacing, is about 515 locations and 436 cells, a 166 kB response.
- **Quota.** Open-Meteo bills one call per location and refuses past 600 locations a minute, 5,000 an hour and 10,000 a day, per IP. The adapter owns these facts (`RATE_LIMIT_WINDOW_S`, `LOCATIONS_PER_WINDOW` in `providers/openmeteo.py`); the use case derives its largest wait (one window plus a small pad) and its location bound (three windows) from them and keeps the policy, so a paid key changes the adapter and a setting only. Locations are fetched in chunks of at most 150 as form posts, under the shared cap of 4 calls in flight, in the plan's order (checkpoint cells first). A cold request that needs at most 600 locations on a fresh window takes about a second; one that needs more (a 10-mile trip across the country: 676 to 1,051 locations in the measurements) waits for the window.
- **Waiting.** The use case owns the wait, so `Outbound` does not change (the adapter only exposes its call and its parsing separately: `request_forecasts` hands opaque raw answers to `parse_forecasts`). A refused chunk (429; a 401 or 403 is credentials and fails at once) is retried after its `Retry-After` plus a second when the delay is given, at most a window plus a small pad (62 s), and `now + wait` is still before the deadline; the fit is checked before sleeping, and the sleep happens after the call has released its outbound slot. Every other refusal is a 503 `provider_limited` at once: a missing delay, a long one (an hourly or daily limit), or a wait that would not fit. A chunk is retried after each of its first three refusals; a fourth refusal is a 503. There is no partial result: a request is complete or an error.
- **Deadline.** One 150 s deadline covers the request's provider work, enough for two full waits and the calls; passing it is a 504 `provider_timeout`. Each Open-Meteo call has a 12 s timeout (a chunk takes about half a second) and one retry on a timeout or 5xx; two timeouts are a 504, other upstream failures and malformed answers a 502.
- **Cache.** The forecast cache holds series by forecast cell and is used only while the series' own first stamp is the request's current UTC hour. It is part of the use case's `Runtime` (the clock, sleep, deadline clock, cache and limits), which tests replace as one object; the process keeps one (`WEATHER_RUNTIME` in `api/api.py`), so every request shares the cache. It is touched only on the event loop, bounded at 3,000 cells (about 38 MB: 1,000 series of 96 hours measured 12.6 MB), and each chunk is parsed and stored as it arrives. When one chunk fails, the others' unfinished calls are cancelled, but a chunk whose response has already arrived is still parsed and stored (in its own task, shielded from the cancellation), so a retry after a 503, 504 or 502 fetches only what is missing. A request reads its clock once: a request that waits across the hour keeps what it holds and never re-reads the cache, which accepts a one-hour approximation at grid hour 0 for late chunks. Concurrent cold requests for the same cells both fetch. It needs one server process to be shared.
- **Open-Meteo's free tier** is non-commercial and requires CC BY attribution; the response carries `attribution: {text, url}` for the UI to show.

**`GET /api/address-search?q=…`** returns US place suggestions from Geoapify's autocomplete with `filter=countrycode:us`. Text with no digit is a city or a place name, so it is searched with `type=city` first, which keeps "Salt Lake" from answering with a town in New Mexico; if that finds nothing, one more search runs without a type, so a depot name stays findable (a failed first call is an error, with no second call). Text containing a digit keeps the untyped search, so a suggestion can be an address, a street or a city. The text is trimmed and must be 3 to 100 characters, checked before any provider call (otherwise 422). The response is `{suggestions: [{label, lat, lon, timezone}], attribution: {text, url}}`: `label` is the full text with the state, `timezone` an IANA name for converting a typed departure time, and the attribution (`Powered by Geoapify`) is what the free plan requires the UI to show. A suggestion without a label, coordinates or time zone is dropped, and no match is an empty list, not an error. A call has a 5 s timeout and is not retried, except that text starting with a number gets 10 s: such a search with no place named is slow (7 to 9 s measured), and no filter or type speeds it up. Its key is `GEOAPIFY_API_KEY`, and a missing one is a 503 `provider_not_configured`.

**Live check.** `backend/live_check.py` (outside `make check`, because it spends TomTom calls; it and `live_address_check.py` share `live_common.py` for set-up, the call budget and the output) runs the endpoint in-process over the seven trips of the feasibility spike, 25-mile spacing and an 80,000 lb load, on 2026-11-12:

|---|---|---|---|---|
| Los Angeles to New York | 3 (2 from TomTom, 1 via Albuquerque) | 14.7 s | 145 kB | 3 |
| Seattle to Miami | 3 | 12.0 s | 181 kB | 1 |
| Chicago to Los Angeles | 2 (no distinct third) on the first run; 3 after the search was widened (see below) | 8.5 s | 66 kB | 3 |
| Dallas to San Francisco | 3 | 8.4 s | 106 kB | 1 |
| Denver to Atlanta | 3 | 4.1 s | 73 kB | 1 |
| Chicago to Indianapolis | 3 | 1.9 s | 12 kB | 1 |
| Dallas to Houston | 3 | 1.6 s | 12 kB | 1 |

Instruction offsets and times stayed cumulative across the two legs of a via route. Lines carry 100 to 2,100 points after reduction. A point in the open Atlantic as origin is a TomTom 400 with the code `MAP_MATCHING_FAILURE`, reported as a 422 `no_route`. On Chicago to Los Angeles the first run tried one city per side, chosen against the fastest route only, and both overlapped. After the search was widened the same trip took 6 TomTom calls (the base call, then Denver at 0.66 overlap, Phoenix at 0.38 and three more that were cancelled once Phoenix filled the gap) and returned three routes in 8.8 s and 100 kB. These are one-off measurements: TomTom's latency on long trips varies a lot between identical calls.

The weather endpoint was run live on 2026-11-13 over Seattle to Miami (the trip with the most locations), 25-mile spacing and 80,000 lb: one TomTom call gave three routes (423 checkpoints), which went back to `POST /api/weather` unchanged. The cold request needed 515 locations (379 checkpoint cells, 136 grid-only; 436 grid cells) in 4 chunks, finished in 1.05 s with no wait and returned 166 kB; the repeat fetched nothing and returned the same body in 0.12 s. `backend/live_weather_report_check.py` runs it; `live_weather_check.py` measures the quota.

Address search was run live on 2026-11-12 over 8 typed queries (a city, an ambiguous name, street addresses with and without a state, and a non-US place): every call answered in 0.7 to 2.8 s, every returned suggestion carried a time zone name, all were US places, and the non-US query returned an empty list.

**Frontend (`frontend/`).** React 19, TypeScript, Vite and Material UI. TanStack Query owns all server requests. The API's types are generated, not written by hand: `src/api/schema.d.ts` comes from the backend's OpenAPI schema (`make types`), and `make check` regenerates it and fails if the committed file differs. `openapi-typescript` declares TypeScript 5 as its peer; `pnpm.peerDependencyRules` in `package.json` allows 6, and the drift check would catch a generator that stopped working. The app has one page, and the code under `src` is split by what it owns:

- `api/` is the typed `fetch` client and its three endpoint calls (routes, weather and address search); its `ApiError` carries the error `code`, and everything that branches on a failure branches on that code.
- `form/` is the trip form: address search (debounced, with the city-first behaviour and the "add the city" hint for number-first text), the departure (now, or a time read in the origin's zone), the load in pounds (empty at the start) and the 10, 25 or 50 mile spacing.
- `plan/` is pure logic with no React: the request bodies, the view of a plan the screens read, the "Why this route?" explanation (first place only, ties marked), and `errors.ts`, one message and one action for every error code in each of three contexts (routes, weather, address). The table is typed over the generated code union, so a code added on the backend fails `tsc` until it has a row. `queries.ts` holds the two planning queries: routes first, then weather once the routes are in. Each is made once per submission and never retried or refetched on its own (no retry, no refetch on focus, reconnect or mount); the global query default in `plan/queryClient.ts` is also no retry.
- `panel/` is the route cards, the "Why this route?" expand, the checkpoint list, the named wait stages, the error notices and the credits. `risk/` owns the five levels' glyphs and colours, so the map, the lists and the key draw one set; `time/` formats times in a named zone.
- `timeline/` is the 0 to 48 hour slider (marks, plus and minus one hour, tap on the track) and the truck positions derived from the checkpoint ETAs.
- `layout/` decides the layout from the viewport (`useLayoutMode`): a bottom sheet with peek, half and full states (dragged by its handle or moved by buttons, and collapsed by Back) below 600 px wide on a tall screen; a side pane from 600 px wide or on a short screen; and from 1700 px the pane with two columns. A tapped spot reads in the sheet on a phone and in a map popup elsewhere. It also holds the error boundary around the map and the focus management, and it makes the map inert behind the phone form.
- `map/` is the one place that imports MapLibre, on the OpenFreeMap Positron basemap (`VITE_BASEMAP_STYLE` at build time can point elsewhere; a plain background replaces it if it cannot load). The page loads it as a separate chunk with its worker, after the form has rendered; ESLint allows only a dynamic `import()` of it, and a type-only import is allowed. The routes, checkpoints (a glyph per level, so the level never depends on colour alone) and the corridor heatmap are GPU layers fed from the plan, not React elements. The slider drives the heatmap by recolouring only the cells whose level changed, with no request. The controller recovers from a lost WebGL context.

Measured on the final build: a scripted drag of the slider across every hour, in headless Chromium at 390 by 844 with touch emulation, 12 drags at 267 and 520 cells, with a 4x CPU slowdown and without. There was no network request, no long task, no `pointermove` event over 16 ms and no frame gap over 50 ms (the worst was 49.9 ms); the frame gap was 16.7 ms at the median and the 95th percentile. The browser drew with software WebGL, so a real phone is unmeasured, and the Chromium build differs from an earlier run of the same measurement, which saw isolated frames of 50 to 133 ms. As built at the M7 closing commit, the gzip sizes are 201.71 kB for the entry, 296.18 kB for the map chunk and 147,800 bytes for the worker (520 kB raw).

Vite forwards `/api` to Django (`vite.config.ts`), so the browser sees one origin.

**Quality gates.** `make test` runs pytest (the endpoints with their providers mocked, the layering and key-leak checks, the settings guard and the risk rules) and vitest (the logic under `plan/`, `timeline/` and `map/`, and component tests for the key states). `make check` adds the generated-types drift check, ruff lint and format checks on the backend, `tsc`, ESLint and Prettier checks on the frontend, and a production build of the frontend, the only check that sees the map's worker file and its separate chunk.

## Hosting

The risk thresholds, load rules and route ranking, the routes and weather endpoints, and the frontend exist (above); what remains is hosting.

| Part | Place |
|---|---|
| Hosting | One container serving the built frontend and the API from the same origin |

Planning is two requests, routes first and weather risk second, so the routes appear on the map before the weather finishes loading.
